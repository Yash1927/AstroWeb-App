Step 1 defaults CORS to deny cross-origin access when `APP_ORIGIN` is absent. Public Home needs no login and returns only card fields for active, listed, profile-saved accounts; email and account state are neither selected nor serialized. Owner and astrologer routes validate request data, return generic service errors and never return hashes or session ids. Both login limiters hash normalized email plus IP before storing the key in process memory. Passwords, cookie values and database errors are not logged.

Sessions are server-side and revocable. The browser receives only a signed random id in a role-specific httpOnly cookie. `Secure` is enabled when `NODE_ENV=production`, SameSite is Lax, and expiry is checked against the database on every protected request. The owner path is `/api/owner`; astrologer and user paths are `/`. User sessions last 30 days and panel sessions last 12 hours. Logout deletes the row before clearing the cookie. Astrologer password replacement, owner reset and owner deactivation revoke every matching astrologer session with one explicit SQL bulk delete; password replacement then issues one fresh session to the current browser.

The Google callback uses GIS's double-submit CSRF value and rejects a mismatch before processing the credential. Token verification stays in the backend. Continuation state is reduced to a URL on `APP_ORIGIN`, so a crafted state cannot create an external redirect. The frontend URL carries only the selected astrologer id and call type; it never carries Google credentials or user details.

Availability reads and writes are protected by the astrologer guard and take their record id only from the session. The replacement transaction uses explicit SQL bulk deletes scoped to that id, cannot target another astrologer and does not mutate bookings. The public slot endpoint accepts only a UUID and listed call type, checks active/listed/profile-saved eligibility before returning data, and exposes only dates, durations and UTC slot boundaries. Prices, private astrologer data and booking participants are not returned.

Booking creation is protected by the user guard and ignores all browser-owned identity, price, duration, call-mode and status values. The service rechecks complete details, canonical required phone, astrologer eligibility and an exact current slot, then reads Settings itself. The transaction expires only the selected astrologer's elapsed holds through one explicit SQL bulk update and lets the database exclusion constraint arbitrate simultaneous overlaps. The mapper recognizes Prisma 8's normalized `sqlState` directly or through a transaction `cause`; callers receive the calm fixed message, never raw database text. Zero-price calls confirm directly; positive-price Normal/Urgent creates only a ten-minute hold and created Payment until a signed provider result arrives.

Razorpay order creation uses the official backend SDK with the Settings amount in whole paise, INR currency, booking receipt and only internal booking/user ids in notes. Standard Checkout is loaded only when payment is needed and receives the public key id plus the server response. Its Astromaitreyi name and same-origin public logo URL are display-only and contain no secret. Browser verification compares the expected and received SHA-256 HMAC bytes with `timingSafeEqual`, then checks that the stored order belongs to the session user and named booking before the settlement transaction. The webhook route preserves raw bytes, caps the body at 64 KiB, authenticates with the separate webhook secret and inserts `x-razorpay-event-id` once. Verification and captured/paid webhooks share the same order-keyed idempotent path. A fee-bearing webhook settles only the stored Settings-backed amount when provider gross minus provider fee matches it. If confirmation hits `Booking_no_overlap` after a hold expires, the gateway reads the provider payment and refunds its full remaining gross amount, including any customer fee, before recording Payment `refunded` and Booking `expired`.

Booking history routes never accept a user or astrologer id. The role guard supplies the subject id and the repository combines it with the requested booking id for direct reads; missing and foreign rows both return `404`. User history selects only public astrologer identity. Astrologer history selects the booked user's permitted birth, gender and phone fields but does not select email, Google subject, credits or unrelated users. HTTP tests request another subject's booking id on both sides and verify the privacy boundary.

Public blog queries select published posts only. A valid user cookie may add the viewer's like and own-comment delete state, but reading never requires a session or completed birth details. Like/comment routes take the user id from the session. Astrologer post and comment mutations combine every id with the session astrologer id; missing and foreign rows share `404`. Invalid author documents return the first fixed schema message so the editor can identify the problem without reflecting submitted text or database details. Own-post deletion bulk-removes only that post's likes and comments before the unique post delete. Owner comment routes remain under the owner cookie path and guard. The comment limiter hashes user id plus IP and permits five accepted submissions per minute in one process; its multi-instance limitation is tracked for Step 16. Comment contents and public avatar keys are never logged, and the API exposes only a commenter's first name and a one-way avatar key.

Image uploads stay behind the astrologer role and temporary-password gate, and profile operations take the subject only from that session. Owner removal has its separate owner guard and validates the target UUID. Multer holds one file in memory with a 5 MB ceiling; `file-type` checks real JPG/PNG/WebP signatures before Sharp decodes, auto-orients, resizes and re-encodes to metadata-free WebP. R2 credentials are backend-only. Blog saves compare every body/cover image to the signed-in astrologer's media rows and configured public URLs, so foreign R2 objects and another astrologer's media cannot be embedded; ownership validation returns `400`, while a missing owned post remains `404`.

The WebSocket upgrade accepts only `/ws` with one validated `role` query, the exact configured `APP_ORIGIN`, and that role's signed server-side session cookie. The role query selects a cookie and never grants authority. On `join`, the database service checks the session subject against the booking's user or astrologer, requires a confirmed in-app booking, and enforces the stored start/end window. Room messages are text-only, limited to 16 KiB, strictly Zod-validated and serialized per socket; signalling and chat are relayed only to the other role in the same booking room. Chat is limited to 500 trimmed characters and one accepted message per second per socket, then discarded rather than persisted. Close reasons stay generic and logs contain no booking ids, session values, chat, SDP, ICE data or personal details.

The ICE-server endpoint independently resolves the user and astrologer cookies, then applies the same participant, confirmed in-app mode and active-window checks. It never trusts the cookie role alone. `TURN_SECRET` remains backend-only. The service derives a base64 HMAC-SHA1 credential for `<booking-end-unix-seconds>:<bookingId>`, so coturn stops accepting it at the booking end. Responses use `Cache-Control: no-store`; missing configuration and internal failures expose only one generic message. No static relay credential is present in frontend code or repository documentation.

The shared browser phone field accepts a local 10-digit number, discards spaces and dashes, and sends `+91XXXXXXXXXX`. This is input assistance only: `PUT /api/me` and phone booking creation still validate the canonical value on the server. Settings refuses a transition from a saved phone to null while a confirmed phone booking ends in the future and returns a field-specific error. Empty birth dates and invalid or future dates receive distinct client messages; the same server date rule remains authoritative.

The service worker has no runtime cache. Its precache contains the user app shell, used Latin/Latin Extended WOFF2 fonts, the manifest and install icons. Owner/astrologer panels, the rich editor, photo cropper and astrologer API stay network-loaded. Navigation fallback denies `/api`, `/ws`, both call-room prefixes and payment/Razorpay paths, so responses containing sessions, personal details, call traffic or payment state are never written to a service-worker cache. The manifest and install assets contain no secret or personal data.

Every route-level generic `503` path now records a fixed operation name through the shared safe logger before returning the public response. Raw caught values are never logged directly. This adds useful server diagnostics without exposing request bodies, sessions or personal data.

`npm audit --omit=dev` reports no production dependency vulnerabilities as of 2026-10-02, including the official Razorpay SDK. The full backend audit reports 5 moderate and 8 high findings in development dependencies; the planned dependency review is tracked in `docs/PROGRESS.md`.
